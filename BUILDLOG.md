# Build Log — AI usage

Honest record of where AI (Claude) helped, where it was wrong, and what I changed. The brief is explicit that "the AI wrote it" isn't an answer for any 2–3 lines an evaluator picks — this log exists so I can point to exactly what I need to be able to explain, and keep myself honest about actually understanding it rather than just shipping it.

## Phase 1 — Design

**What AI did:** Drafted the full `DESIGN.md` (data model, API surface, layer sketch, non-goal) from the capstone brief in one pass, based on decisions I made first (widget types: signup form + CTA popover; auth: reuse the Supabase pattern from `auth-api` rather than API keys, for consistency with existing work).

**What I need to be able to explain:** why `tenant_id` is denormalized onto `submissions` instead of only living on `widgets` (query performance — every dashboard/access-control check needs it without a join), and why the non-goal is a widget-builder UI specifically rather than something else (the brief grades the backend, not a frontend product).

## Phase 2 — The hardened submission path

**What AI did:** Built the full layered implementation — schemas, routes, services, repositories, core (auth/rate-limit/spam), db models, the vanilla-JS embed loader, and the test suite (24 tests: CRUD, tenant isolation, validation, honeypot, rate limiting, CORS preflight, enrichment fallback chain via a fake transport).

**What I need to be able to explain:**
- Why `fetch()`-equivalent network failures in `enrichment_service.py` are caught and turned into `(None, None, None)` rather than raised — enrichment failing must never fail the submission itself, so the function's contract is "never raises."
- Why the rate limiter is two independent instances (`ip_limiter`, `widget_limiter`) rather than one shared one — a flood from one visitor shouldn't lock out everyone else on the same widget, and a genuinely popular widget shouldn't look like an attack just because many different real people use it.
- Why the honeypot check returns a success-shaped response with `id: null` instead of an error — telling a bot "rejected, honeypot detected" just teaches it to remove that field next time; the response gives it no signal to react to.
- Why `get_public()` (unscoped) exists at all alongside the tenant-scoped `get()` — the public delivery/config/submission endpoints genuinely need to look up a widget without knowing who owns it (any visitor on the internet can load any customer's embedded widget), while every authenticated management route must never use it.

**Two real bugs found and fixed — not by AI catching them in advance, but by actually running the test suite and reading the failures:**

1. **Test fixture collision.** `client` and `client_as_tenant_b` fixtures each hardcoded a different tenant id via `app.dependency_overrides` — but that dict lives on the shared `app` object, not per-TestClient. When a test used both fixtures together, whichever fixture ran its setup last silently won for *both* clients. Result: the tenant-isolation tests were passing, but for the wrong reason — both simulated clients were actually the same tenant the whole time. Caught this by doing a negative-control check (deliberately breaking real tenant isolation in `widgets.py` and confirming the test failed) — it didn't fail, which is what exposed the fixture bug. Fixed by deriving tenant identity from each `TestClient` instance's own persistent `Authorization` header instead of two competing global overrides.

2. **Test-isolation leak via module-level env vars.** `test_submissions.py` originally set `ENRICHMENT_FORCE_A_DOWN`/`B_DOWN` as bare `os.environ[...] = "1"` at module level. This runs during pytest's *collection* phase — before any test executes — so it silently affected `test_enrichment.py`'s assertions when the full suite ran together, even though `test_enrichment.py` passed cleanly when run in isolation. Fixed with a `monkeypatch`-based `autouse` fixture instead, which pytest correctly scopes and reverts per-test.

**What I changed / pushed back on:** Rejected the first `seed.py` draft's design, which required a real Supabase user id as an argument (`python -m app.seed <tenant_id>`) — it didn't match the `seed:` command already committed in `capstone.yaml` (`python -m app.seed`, no args), and would have made "a stranger can run this in under 5 minutes" false for anyone without a pre-existing Supabase account. Fixed by using a fixed demo tenant id (no FK constraint to a real Supabase user — `tenant_id` is a plain string column) and fixed, non-random widget IDs for the two seeded demo widgets specifically, so `customer-site/index.html` can reference a stable, known widget id that works identically on any machine right after `docker compose up` + seed, rather than requiring a lookup step first.

## Phase 3 — Delivery, dashboard & proof

**Real bug found: the fallback-chain proof depended on the real internet being reachable, which the brief explicitly says not to do.** The original `enrichment_service.py` only let you force a provider *down* via env var (`ENRICHMENT_FORCE_A_DOWN`); a provider that wasn't forced down always made a real call to `ip-api.com` / `ipapi.co`. That means "prove provider A down → provider B answers" only worked if B's real API happened to be reachable at proof time — and in one build/verification environment, neither provider was reachable at all (`ip-api.com` → `403`, `ipapi.co` → connection failure, both blocked by that environment's own network policy). Re-reading the brief caught the actual spec: Section 7 asks for "one mock provider that always answers, one you can toggle down" — a fully deterministic proof, not one that depends on two third-party APIs staying up and reachable. Fixed by adding `ENRICHMENT_MOCK=1`, which swaps both providers to canned, instant responses with no network call at all; `ENRICHMENT_FORCE_A_DOWN`/`_B_DOWN` then layer on top of that exactly as before. Without the flag, both providers still hit the real APIs unchanged, for actual local development. This is the correct fix, not a workaround for one sandbox's restrictions — the fallback proof now can't fail just because a geo API had downtime or changed its response shape on evaluation day.

**What I need to be able to explain:** why `ENRICHMENT_MOCK` is a separate flag from `ENRICHMENT_FORCE_A_DOWN`/`_B_DOWN` rather than folded into them — because "always answer with fake data" and "pretend to be down" are independent, composable choices (you need both together to prove the *fallback*, but each is also independently useful: mock-without-force proves the happy path is deterministic too, force-without-mock is closer to real production behavior for manual dev).

**Real bug #2, found only once `docker compose up --build` ran against real Postgres.** `python -m app.seed` failed with `sqlalchemy.exc.DataError: ... StringDataRightTruncation: value too long for type character varying(36)`. `app/db/models.py` sizes `tenant_id` as `String(36)` — exactly a real UUID's length — but `app/seed.py`'s `DEMO_TENANT_ID` was `"demo-tenant-00000000-0000-0000-0000-000000000000"`, 48 characters. SQLite silently accepts oversized strings in a `VARCHAR(36)` column (it doesn't enforce the length at all); Postgres enforces it and rejected the insert. Every SQLite-backed test and local dev run passed cleanly the whole time — this bug was completely invisible until the Docker/Postgres run the brief's own `$0 stack` table lists as the real target environment. Fixed by shortening the constant to `"00000000-0000-0000-0000-000000000000"` (36 chars, same style as the two fixed demo widget IDs).

**What I need to be able to explain:** why this didn't show up in 24 passing tests — the test suite runs against SQLite (see `tests/conftest.py`), and SQLite's type system is dynamic: a column declared `VARCHAR(36)` is only a hint there, never actually enforced on insert. It's a real, common gap between "tests pass" and "works against the real database" — which is exactly why the brief lists Postgres via Docker as the target environment rather than treating SQLite as equivalent.

Also completed this phase, with real evidence in `EVIDENCE.md`: full Docker Compose run against Postgres, a real Supabase signup/login (not the test-only bearer-token stand-in), an authenticated widget created under that real account, live tenant isolation confirmed against two genuinely different Supabase users, and a real public submission confirmed visible through the dashboard API — closing Probe 1's "...and visible via the dashboard API" clause and the Documentation checkbox.
